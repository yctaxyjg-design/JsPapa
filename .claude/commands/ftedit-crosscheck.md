# FT Edit 분석 크로스체킹

## 대상 파일 찾기

`$ARGUMENTS`에 경로가 있으면 그것을 쓴다. 없으면 세션 첨부파일과 업로드 폴더를 확인한다:
`ls -t /root/.claude/uploads/*/ 2>/dev/null`

찾아야 할 것은 **두 종류**다.

1. **GPT 분석** — `YYYYMMDD_ftedit.md`
2. **FT 기사 원문** — 사용자가 iCloud Drive `ft edit` 폴더에 보관한다

**iCloud Drive는 원격 컨테이너에서 접근 불가**하므로 원문도 첨부돼야 읽을 수 있다.
분석만 있고 원문이 없으면 **Track B로 진행하되, 그 사실과 원문을 첨부하면 무엇이 더 검증되는지 먼저 알린다.**
분석 파일조차 없으면 추측하지 말고 요청 후 중단한다.

## 절차

`ftedit/PROTOCOL.md`를 읽고 그대로 따른다. 요약하면:

1. **트랙 판정** — 원문 있으면 Track A, 없으면 Track B. 결과 문서 첫머리에 명시
2. **(Track A) 원문을 분석보다 먼저 읽는다.** 순서가 핵심 — 분석을 먼저 읽으면 그 프레임에 갇혀 누락을 못 찾는다
3. 분석 문서에서 검증 가능한 주장 추출 (수치 → 인과·귀속 → 구조 → 최상급 → 반사실 순)
4. **알려진 반복 오류 패턴(P1~P6)부터** 훑는다
5. 기사당 1~2회 `WebSearch`로 외부 대조. Track A에서도 생략하지 않는다 — 원문 대조는 "GPT가 FT를 옳게 읽었나", 외부 대조는 "FT가 옳았나"로 서로 다른 질문이다
6. Tier 0(FT 원문 오류) / Tier 1(사실오류) / Tier 2(분석적 누락) / Tier 3(잘한 점)로 분류. Track A에서는 Tier 1을 오독·창작·오귀속으로 세분
7. 고정 5축 채점. Track B면 미검증 축을 표에 표시
8. 구조적 패턴 진단 + 다음 회차 프롬프트 개선 제안
9. `ftedit/crosscheck/YYYY-MM-DD.md`에 저장, 출처 URL 첨부, 커밋

## 반드시 지킬 것

- **저작권**: JsPapa는 공개 저장소다. FT 원문 전문·상당 부분을 커밋하지 않는다. 검증용으로 읽되 인용은 기사당 200~300자 이내, 인용보다 해설이 길어야 한다
- Track B면 **"분석의 오류인지 FT 원문의 오류인지 구분되지 않는다"**를 문서 첫머리에 명시하고, 「FT senior editor의 시각」 섹션은 검증 불가로 표시
- 기업 계약·금융 수치는 **PR Newswire 원문 보도자료**가 가장 정확. 언론 요약 헤드라인은 조건부 최대치를 확정액으로 뽑는 경향이 있으니 주의
- Tier 3(잘한 점)을 생략하지 않는다
- 검증 못 한 항목은 검증 못 했다고 쓴다
- 직전 회차 `ftedit/crosscheck/` 파일을 읽고 **패턴 재발 여부**를 언급한다. 트랙이 다르면 점수를 나란히 비교하지 않는다
