# FT Edit 일일 분석 크로스체킹 프로토콜

GPT가 매일 생성하는 `YYYYMMDD_ftedit.md`(FT Edit 기사 심층분석)를 받아 **사실 검증 + 품질 평가**를 수행하는 절차.

## 입력 자료

사용자는 FT 유료구독자이며 기사 원문을 iCloud Drive의 `ft edit` 폴더에 보관한다.

**단, 이 저장소의 작업 세션은 원격 컨테이너에서 실행되므로 iCloud Drive에 접근할 수 없다.**
(`scripts/economist/save_analysis.sh`가 iCloud 경로 부재 시 로컬로 폴백하는 것과 같은 제약)
→ 원문·분석 모두 **세션에 첨부**되어야 읽을 수 있다.

따라서 아래 2트랙으로 나뉜다. 매 회차 어느 트랙인지 결과 문서 첫머리에 명시한다.

### Track A — 원문 있음 (권장)

읽는 순서를 지킨다: **① FT 원문 → ② GPT 분석 → ③ 외부 크로스체킹**

원문을 먼저 읽어야 분석에 끌려가지 않는다. 분석을 먼저 읽으면 그 프레임으로 원문을 보게 되어 누락을 못 찾는다.

Track A에서만 검증 가능한 것 (Track B에서는 원리적으로 불가):

| 항목 | 왜 원문이 필요한가 |
|---|---|
| **오류 책임 소재** | 오류가 GPT의 것인지 FT의 것인지 확정. 전자면 프롬프트 문제, 후자면 FT를 걸러 읽어야 한다는 뜻 — 대응이 완전히 다르다 |
| **「FT senior editor의 시각」 전체** | 리드 구성·문단 배치 순서·인용 위치 분석. 원문 없이는 검증률 0% |
| **「생략된 논점」의 진위** | 기사가 뺀 것 vs 분석이 못 찾은 것을 추정이 아니라 확정 |
| **수치 인용 정확도** | 원문 숫자와 1:1 대조 → P1 패턴을 추정에서 증명으로 |
| **인용문 정확도** | 분석이 인용부호로 감싼 문장이 실제 기사에 있는지 |

### Track B — 원문 없음 (폴백)

- FT 원문 유료화로 **"기사에 실제로 그렇게 쓰였는지"는 검증할 수 없다.**
- 검증 대상은 **분석이 사실로 진술한 내용 vs 공개 보도**의 대조로 축소된다.
- 분석의 오류인지 FT 원문의 오류인지 구분되지 않는 경우가 있다. 그럴 땐 그렇게 쓴다.
- 「FT senior editor의 시각」 섹션은 **검증 불가**로 명시하고, 검증했다고 쓰지 않는다.

## ⚠ 저작권 가드레일

JsPapa는 **공개 저장소**다. FT 원문은 유료 보도자산이고 구독은 본인 열람권만 부여한다.

- **원문 전문·상당 부분을 `ftedit/` 이하에 커밋하지 않는다.** 검증용으로 읽기만 하고 저장소에는 남기지 않는다.
- 크로스체킹 문서에는 검증에 필요한 최소 인용만 쓴다 (기사당 누적 200~300자 이내).
- 인용보다 해설이 길어야 한다.
- 원문 파일은 첨부 상태로만 다루고, 필요하면 스크래치패드 디렉터리에 둔다.

## 절차

### 1. 수집 대상 파악
분석 문서에서 기사 제목 목록과, 각 기사별로 **검증 가능한 주장**을 뽑는다. 우선순위 순:

1. **고유 수치** — 금액, 면적, 인원, 비율, 기간
2. **인과·귀속 주장** — "A가 B를 가능하게 했다", "X 때문에 Y가 죽었다"
3. **구조 서술** — 계약 조건, 지분율, 제도 설계
4. **최상급·최초 주장** — "사상 처음", "최대", "최악"
5. **반사실** — "만약 ~했다면 ~했을 것이다"

### 1-A. (Track A 전용) 원문 대조
분석을 읽기 **전에** 원문을 읽고 기사별로 다음을 기록한다.

- 핵심 수치 원문 문자열 그대로 (`"9.97mn tonnes"`)
- 리드 구성과 문단 배치 순서 (「FT senior editor의 시각」 검증용)
- 인명 피해·인과 문장이 어느 사건의 것인지
- 계약·금융 구조 4항목 (단위·기간·확정여부·에스컬레이터)

그 다음 분석을 읽으며 **원문에 없는 진술**과 **원문과 어긋난 진술**을 분리한다. 전자는 GPT의 창작/오귀속, 후자는 GPT의 오독이다. 원문에 있는데 공개 보도와 다르면 **FT 원문의 오류**다 — 이 경우 GPT를 탓하지 않고 그렇게 적는다.

### 2. 외부 대조
기사당 1~2회 `WebSearch`. 8개 기사 전부를 같은 깊이로 파지 말고, **수치 밀도가 높은 기사부터** 검증한다. 통상 6건 실질검증이면 판정에 충분하다.

Track A에서도 외부 대조는 생략하지 않는다. 원문 대조는 "GPT가 FT를 옳게 읽었나"를, 외부 대조는 "FT가 옳았나"를 본다. 둘은 다른 질문이다.

원 기사가 FT라도 통신사·업계지·기업 보도자료가 같은 사실을 다룬다. 특히:
- 기업 계약/금융 → **PR Newswire 원문 보도자료** (가장 정확)
- 통계 → 원 발표기관 (국가통계국, 유로스타트, CDC 등)
- 사건 피해 → 복수 매체 대조 (단일 매체 수치는 초기 보도일 수 있음)

### 3. 판정 등급

| 등급 | 기준 |
|---|---|
| **Tier 1 — 사실오류** | 공개 보도와 어긋남. 반올림 오차는 제외하되 성격이 바뀌면 포함 |
| **Tier 2 — 분석적 누락** | 사실은 맞지만, 빠진 정보가 분석의 논증을 바꾸는 경우 |
| **Tier 3 — 잘한 점** | 유지·강화할 판단. 반드시 포함할 것 (품질평가는 감점표가 아니다) |
| **Tier 0 — FT 원문 오류** | (Track A 전용) 분석은 원문을 옳게 옮겼으나 원문 자체가 공개 보도와 어긋남. GPT 책임이 아니므로 품질점수에서 분리한다 |

Track A에서는 Tier 1을 다시 갈라 적는다: **오독**(원문과 어긋남) / **창작**(원문에 없음) / **오귀속**(원문의 A를 B에 붙임). 오늘 관측된 P2(인접 사실 병합)는 오귀속에 해당하며, 원문이 있어야 확정된다.

### 4. 품질 축 (5개 고정)

매번 같은 축으로 채점해 **회차 간 비교가 가능하게** 한다.

- 사실 정확도
- 증거 등급 구분 (회사 발언 / 업계 자료 / 공개 데이터를 구분하는가)
- 논증 구조 (편집 배열 분석, 생략 논점, 관통 프레임) — **Track A에서만 실측 가능**
- 반증 규율 (자기가 인용한 데이터로 자기 논증을 검증하는가)
- 프레임워크 절제 (오스트리아 학파 등을 억지로 끼워맞추지 않는가)

Track B로 채점했다면 어느 축이 미검증인지 표에 적는다. 트랙이 다른 회차끼리 점수를 나란히 비교하지 않는다.

### 5. 구조적 진단
개별 오류를 넘어 **반복될 패턴**을 지목한다. 단발 실수와 파이프라인 결함을 구분하는 것이 이 프로토콜의 핵심 가치다.

### 6. 산출물
`ftedit/crosscheck/YYYY-MM-DD.md`로 저장하고 커밋한다. 출처 URL 목록을 반드시 첨부한다.

## 작성 원칙

- **Tier 3(잘한 점)을 빼지 않는다.** 매일 감점만 쌓으면 개선 신호가 사라진다.
- 오류의 **결과**를 쓴다. "숫자가 틀렸다"가 아니라 "이 숫자가 틀려서 논증이 어떻게 뒤집힌다"까지.
- 검증 못 한 항목은 **검증 못 했다고 쓴다.** 확인된 것과 미확인을 섞지 않는다.
- 분석 문서가 스스로 「프롬프트 개선」 섹션을 갖고 있으므로, 제안은 그 섹션에 붙일 수 있는 형태로 쓴다.
